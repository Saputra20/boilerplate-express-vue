## 2. Outcome
Add a public `/reset-password?token=…` page compatible with the actual recovery email URL. It submits a new password and the in-memory token to the approved reset-confirm API, displays the backend’s combined invalid/expired/used-link result safely, and directs successful users to login after the backend has revoked their sessions.

Set an early `no-referrer` policy in the CMS document before app scripts load; deployment access logs must redact query strings for this route.
- Add API client method and request schema for `POST /api/v1/auth/password-reset/confirm` with `{ token, password }`.
- Form fields: new password and confirmation. Confirmation is frontend-only and excluded from request. Match backend password policy exactly: 12–128 Unicode code points, no trimming, no composition requirements; backend remains authoritative.
- Use the shared TailAdmin auth layout and existing password/input/button/feedback primitives.
- Render initial ready-to-submit, missing link, submitting, local validation, combined invalid/expired/used token, generic server/network failure, and success states.
- On `204`, explain that reset completed and sessions were revoked; provide a return-to-login action. Do not apply authenticated state.
- Add focused tests with existing Vitest/jsdom/Vue Test Utils.

## 8. Implementation Requirements
- Email link is exactly `<PUBLIC_APP_URL>/reset-password?token=<raw-token>`. CMS route suffix is `/reset-password`; token is the `token` query value. A URL route token must not be introduced.
- On page entry, distinguish only absent token vs present token. There is no API to determine whether a present token is valid before submission. Submit token only when user submits a locally valid form.
- Remove `token` from the browser address bar with history replacement after reading it, retaining the token in component memory until submit or navigation. Do not store it in localStorage, sessionStorage, persisted Pinia, telemetry, logs, error messages, or analytics. Never include it in a redirect target.
- API request is strict `{ token: string, password: string }`; success is `204 No Content`. No bearer auth is required or used.
- Backend token format is exactly 43 URL-safe base64 characters and TTL one hour. Backend consumes it once, only while unexpired and active. Unknown, expired, revoked, and used tokens all return `400` with code `invalid_or_expired_password_reset_token`; do not claim to distinguish them.
- Password: retain exact input including whitespace; backend accepts 12–128 Unicode code points. Frontend should use same policy for immediate feedback; confirmation equality is frontend-only. Do not add uppercase/digit/symbol/composition rules.
- `400 { message: "Bad request" }` may represent malformed input or password policy failure and does not provide a distinct password-policy code. Map to a safe form-level message; don't show raw internal content. `429 { message: "Too many requests" }` is the source-IP cap of 20 attempts per 15 minutes. Safe `500`, timeout, network, and invalid response stay generic.
- Success resets password, clears `mustChangePassword`, and revokes every active session and refresh token atomically. Do not call `/me`, refresh, or auto-login; direct the user to `/login`.
- Route is public. Keep the UI consistent with shared auth layout; prevent duplicate submit and keep password material out of logs/state.

## 9. Applicable Contracts
**API Contract**

| Method | Path | Auth | Request | Success | Errors |
| --- | --- | --- | --- | --- | --- |
| POST | `/api/v1/auth/password-reset/confirm` | None | Strict `{ token: string, password: string }` | `204 No Content` | `400 { message: "Bad request" }` for malformed/password policy; `400 { message: "Invalid or expired password reset token", code: "invalid_or_expired_password_reset_token" }` for any unusable challenge; IP `429 { message: "Too many requests" }`; sanitized `500` |

**Link Contract:** Backend `buildAuthActionUrl(baseUrl, 'reset-password', token)` appends `/reset-password?token=<URL-encoded token>` to `PUBLIC_APP_URL` after normalizing its trailing slash. Token: 32 random bytes, base64url (43 characters), expires in one hour, single-use. No GET validation.

**UI Contract:** Public `/reset-password`; password and confirmation controls. Confirmation stays frontend-only. No auth/session state changes; successful reset links to login.

## 11. Runtime Behavior
Open email URL → router resolves public reset path → read query token into local component memory → replace browser URL to remove sensitive query → if token absent show invalid-link state; if present show form without making a preflight call → validate password and confirmation → `POST /api/v1/auth/password-reset/confirm` with exact token and password → `204` shows success and login link; invalid/expired/used token code shows one combined link-error state; `400` password/malformed errors show safe validation feedback; `429` and transport/server failures show safe retry guidance. Successful reset does not authenticate the browser; backend revokes existing sessions.

## 12. Error And Edge Cases
| Scenario | Expected Result | Security / Recovery |
| --- | --- | --- |
| Missing query token | Invalid-link state and request-new-reset link | No API request; no invented token |
| Present malformed/unknown token | Submit to actual endpoint; combined invalid/expired result | No separate client preflight or token echo |
| Expired/revoked/consumed token | Same combined `invalid_or_expired_password_reset_token` state | Backend intentionally does not distinguish |
| Password under/over policy | Local matching length feedback, backend `400` safely mapped | Count Unicode code points; do not trim |
| Confirmation mismatch | Local confirmation error; no request | Confirmation never enters API body |
| Submit pending/repeat | One request; inputs/action disabled | Avoid duplicate consume attempts |
| `429`/network/timeout/5xx | Safe retry/error guidance | No token/password in message or logs |
| Success `204` | Success and login action | Sessions revoked; no auto-login |
| Refresh/direct URL after token scrub | No token in address, so missing-link state | Do not recover token from storage |

## 13. Security Requirements
Keep raw reset token only in short-lived component memory, clear it on navigation/unmount, and replace token query from visible URL history. Never store or log it, the new password, or confirmation. Avoid analytics/telemetry leakage and open redirects. Never include token in error/returnTo. Do not expose backend details or infer token validity before confirmation. Do not claim automatic session revocation on client; backend is authoritative.
